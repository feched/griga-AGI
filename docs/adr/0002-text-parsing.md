# ADR-002: Построение графа из текста

**Статус:** accepted
**Дата:** 22.11.2026
**Связанные доки:** ARCHITECTURE.md §2, §4.2; ADR-001; GLOSSARY.md

## Контекст

Граф знаний нужно чем-то наполнять. На v0.1 вход — только текст.
Нужно определить: как из предложения получаются узлы и рёбра,
не скатываясь в хардкод (списки правил на каждое слово), который растёт
бесконечно.

От этого зависит: §2.5, §4.2 ARCHITECTURE; валидация (ADR-008);
канонизация (ADR-001).

Рассматривались варианты:
1. Шаблоны (regex) — контроль, но утопает в морфологии языка.
2. Только NLP-парсер — даёт синтаксис, но не даёт тип отношения.
3. Гибрид: парсер для структуры + правила для смысла.
4. Своё.

## Решение

**Вариант 3 (гибрид): локальный NLP-парсер + дистрибутивные векторы +
минимальная онтологическая рамка + один алгоритм построения рёбер.**

### Три выхода Perception (Парсера)

Парсер возвращает не просто список слов, а три потока данных:
1. **Узлы (Nodes):** концепты для активации (`[трава]`, `[синий]`).
2. **Утверждения (Statements):** что именно нужно записать в граф.
   - *ППолярность (Polarity)*: отрицание («Трава НЕ синяя»). Это не тип ребра. Это флаг в метаданных утверждения (asserted, negated, unsure). В базу знаний (durable graph) пишутся только факты со статусом asserted. Вопросы (speech_act = question) никогда не записываются как факты.
   - *Модальность (Modality):* уверенность/сомнение («Наверное, трава зеленая» -> `confidence = medium`).
3. **Диалоговые маркеры (Markers):** тип реплики.
   - *Speech Act:* это был вопрос или утверждение? («Трава зеленая?» vs «Трава зеленая.»).
   - *Эмоция:* грусть, радость, агрессия.
   - *Атрибуция:* кто это сказал («Вася сказал, что...»).

### Компоненты (локальные библиотеки, не API)

- **Парсер языка** (spaCy / Natasha для русского; аналоги для других языков) — части речи, синтаксическое дерево.
    **Языко-зависимый компонент**. Русская модель не разбирает английский.
    v0.1: только русский. Добавление языка = подключение модели парсера,
    алгоритм и рамка не меняются.
- **Дистрибутивные векторы** (fastText / word2vec) — векторы слов для
  определения синонимов. Локально, бесплатно.

Это **библиотеки**, а не сторонние API — не нарушает ограничение VISION §8.

### Минимальная онтологическая рамка (3 правила, не растёт)

| Часть речи (от парсера) | Роль в графе |
|---|---|
| существительное | узел-концепт |
| глагол | узел-отношение |
| прилагательное | узел-свойство |

**Запрет на расширение.** Если встречается случай, требующий четвёртого
правила — это не повод добавлять правило. Варианты:
(а) вывести из структуры/векторов; (б) признать ограничение v0.1;
(в) вынести в ADR как research-вопрос.

Обоснование: правила привязаны к **категориям** (части речи), а не к словам.
Новый глагол не добавляет правило — он попадает в существующее. Рамка конечна.

### Алгоритм построения рёбер (один, не растёт)

Обход синтаксического дерева:
1. Найти глагол-сказуемое.
2. Найти его субъект (подлежащее).
3. Найти его дополнения и обстоятельства (зависящие от глагола).
4. Для каждого дополнения/обстоятельства создать ребро:
   `[субъект] ──(глагол_предлог)──> [объект]`.
   Если предлога нет — имя отношения = глагол.
5. Если глагола нет (именное сказуемое, «X — это Y»):
   тип связи определяется структурой (см. ниже).

Это **один алгоритм** для всех предложений. Новое слово не добавляет шаг.

### Тип связи — из структуры, не из списка

Базовые типы (ADR-001: `это`, `часть`, `свойство`, `связано_с`)
определяются **по структуре**, а не по списку слов:

- `это` — если объект является классом/категорией субъекта
  («трава — это растение»: растение — класс, трава — экземпляр).
- `свойство` — если объект — прилагательное («трава зелёная»).
- `часть` — если связь «X является частью Y» (определяется по структуре
  «X — часть Y» или «Y состоит из X»).
- `связано_с` — всё остальное (глагольные отношения, ассоциации).

Точные критерии различения — TBD (уточнить на практике, ADR-TBD).

### Канонизация — через векторы, не через список

Имя отношения берётся из текста (глагол + предлог): `растёт_на`,
`произрастает_в`. Синонимы склеиваются **автоматически**:
- векторы `растёт_на` и `произрастает_на` близки → один кластер → канон.
- порог близости — TBD (уточнить на практике).

**Не** ручной список синонимов. Список — только для стартовой калибровки,
не для работы.

### Пошаговый пример

Предложение: «Трава растёт на газоне.»

1. **Парсер:** `трава` (сущ., субъект), `растёт` (глагол, сказуемое),
   `на газоне` (сущ., обстоятельство места).
2. **Рамка:** `трава` → концепт, `растёт` → отношение, `газон` → концепт.
3. **Алгоритм:** глагол `растёт` + предлог `на` → имя `растёт_на`;
   субъект `трава`, объект `газон` → ребро.
4. **Канонизация:** вектор `растёт_на` — проверка на синонимы (пока нет
   других, остаётся `растёт_на`).
5. **Создание:** `[трава] ──(растёт_на)──> [газон]`, с метаданными
   (источник = текст, уверенность = средняя).

Предложение: «Трава — это растение.»

1. **Парсер:** `трава` (сущ., субъект), `растение` (сущ., именная часть),
   `это` — связка.
2. **Рамка:** оба существительных → концепты.
3. **Алгоритм:** глагола нет, именное сказуемое → тип связи из структуры:
   `растение` — класс → `это` (is-a).
4. **Создание:** `[трава] ──(это)──> [растение]`.

Предложение: «Трава зелёная.»

1. **Парсер:** `трава` (сущ.), `зелёная` (прил.).
2. **Рамка:** `трава` → концепт, `зелёная` → свойство.
3. **Алгоритм:** прилагательное при существительном → `свойство`.
4. **Создание:** `[трава] ──(свойство)──> [зелёная]`.

## Альтернативы

- **Вариант 1 (только шаблоны):** отклонён — утопает в морфологии
  языка, шаблонов нужно бесконечно много, растёт хардкод.
- **Вариант 2 (только парсер):** отклонён — даёт синтаксис, но не даёт
  тип отношения; без рамки непонятно, что с выходом парсера делать.
- **Вариант 4 (своё):** отдельный research, не MVP.

## Последствия

**Плюс:**
- Не растёт: 3 правила рамки + 1 алгоритм. Новые слова не добавляют код.
- Контролируемо: выход парсера виден, логика поверх — своя.
- Согласуется с ADR-001: канонизация через векторы, реификация из текста.
- Локально: библиотеки, не API. Не нарушает VISION §8.

**Минус / цена:**
- Зависимость от качества парсера (ошибки разбора → ошибки графа).
- Векторы требуют начальной калибровки (порог близости).
- Тип связи (это/часть/свойство) — эвристика по структуре, не всегда точная.
- Ограничение v0.1: только текст. Видео/звук — позже (ADR-TBD).

**Что разблокирует:**
- §2.5, §4.2 ARCHITECTURE — как строить граф.
- ADR-008 (валидация) — понятно, что проверять.
- ADR-013 (причинность) — парсер должен уметь извлекать причинные конструкции
  («X вызывает Y»), когда причинность появится.
