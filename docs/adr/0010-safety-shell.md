# ADR-010: Safety shell, approval-gate и пороги аномалий

**Статус:** accepted
**Дата:** 24.11.2026
**Связанные доки:** ARCHITECTURE.md §7; ADR-008; ADR-015

## Контекст

ARCHITECTURE §7 требует внешний слой, который проверяет Гришу снаружи:
approval-gate для критических действий, аудит изменений и пороги
аномалий. В v0.1 опасных действий нет (ADR-015: без веб-поиска, кода и
самоизменения), но интерфейсы (Telegram/VK/web) появятся позже, и
safety-контур должен существовать до них, а не после.

Принцип: **safety, который агент может изменить — не safety.** Поэтому
shell не читает граф, не зависит от Perception/Speech и не даёт агенту
права подтверждать собственные действия.

## Решение

### Классы действий

| Класс | Примеры | Политика v0.1 |
|---|---|---|
| `safe` | чтение графа, активация, генерация ответа | разрешено |
| `guarded` | запись факта, обновление веса, забывание | разрешено, но аудируется |
| `approval` | удаление факта, отправка сообщения от имени пользователя | запрещено: approver в CLI нет |
| `forbidden` | исполнение кода, веб-поиск, запись файлов, самоизменение | запрещено всегда |

Класс задаётся вызывающей стороной вместе с действием; shell не пытается
угадать намерение по тексту. `SafetyShell.check(action)` возвращает
вердикт, `SafetyShell.enforce(action)` — вердикт плюс запись в audit-log.

### Approval-gate

- Подтверждение может дать только создатель; в v0.1 его нет, поэтому
  `approval`-действия по умолчанию запрещены.
- Флаг `approved=True` существует для тестов и будущего UI; CLI его не
  выставляет.
- После `max_forbidden_attempts` (по умолчанию 3) запрещённых попыток
  shell блокируется до перезапуска процесса.

### Пороги аномалий

На каждом ходу `Dialogue` передаёт в `observe_turn()` счётчики
`new_nodes`, `new_edges`, `conflicts`. Пороги живут в `config.toml`:

```toml
[safety]
max_new_nodes_per_turn = 40
max_new_edges_per_turn = 20
max_conflicts_per_turn = 1
max_forbidden_attempts = 3
```

Превышение не откатывает уже проверенную запись (валидация ADR-008
срабатывает раньше), но фиксируется как `anomaly` в audit-log и
возвращается в `TurnResult.anomalies`. Это сигнал для отладки волны и
повод ужесточить парсер, а не «тихая» потеря данных.

### Аудит

Все решения shell и аномалии пишутся в `graph_events`:

- `entity_type = "safety"`;
- `entity_id` — фиксированный UUID пространства safety;
- `action` — `allow` / `deny` / `anomaly`;
- `after` — имя действия, класс, причина, актор, счётчики;
- `source = "safety_shell"`.

`griga history` показывает эти события вместе с изменениями графа.

## Последствия

- Опасные действия невозможно выполнить «в обход»: интерфейсы обязаны
  звать `enforce`, а не писать в граф напрямую.
- Пороги калибруются в `config.toml`, без правки кода.
- v0.1 остаётся безопасным по построению: единственные разрешённые
  записи — факты, прошедшие валидацию.
- Появление реальных инструментов потребует отдельного approver-интерфейса;
  это расширение ADR, а не изменение принципа.
